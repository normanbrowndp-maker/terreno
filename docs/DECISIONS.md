# Решения и открытые архитектурные вопросы

## ADR-014 — транзакционный bootstrap как подготовленный артефакт

TRAVEL-024: точные SQL00_inspect/10_prepare/20_verify и local rehearsal подготовлены без Neon SQL. Новые роли планируются NOLOGIN; bootstrap→migrator downward membership явно административная, app-роли не наследуют admin. Передача DB ownership обусловлена действующим guard/неизменной migration003; мигратор остаётся доверенной DDL-ролью. После migrations повторный10 запрещён inventory-gate, восстановление начинается с read-only inspect-recovery. Catalog runtime остаётся read-only; будущие private identity/trips writers проектируются отдельно. [Доказательства и ограничения](NEON_BOOTSTRAP_REPORT.md).

## ADR-013 — metadata discovery отделён от connection approval

TRAVEL-023 разрешает локальную регистрацию metadata, но не SQL/bootstrap/credentials. Активный schema требует runtime/migration roles, ещё не подтверждённых; поэтому реальная запись помещается в strict pendingTargets со state=pending-bootstrap и только известным bootstrapOwner. targets остаётся пустым; resolver выбирает только active targets. Unknown/duplicate records и любые попытки трактовать pending как active отвергаются. [Результат](NEON_TARGET_REGISTRATION.md), [следующий bootstrap scope](NEON_BOOTSTRAP_PLAN.md).

## ADR-001 — Форма приложения и стек

**Статус:** принято владельцем 2026-11-18: Next.js+TypeScript модульный монолит, PostgreSQL/PostGIS, API v1 с возможностью будущего mobile client.

**Вопрос:** один web-продукт небольшой команды или API сразу для нескольких независимых клиентов?

**Рекомендация:** TypeScript/Next.js модульный монолит + PostgreSQL/PostGIS, pg/SQL migrations. Один deployment, общие use cases и явные границы. Альтернатива — отдельный NestJS/Fastify backend при подтверждённом втором клиенте/команде. Последствия: меньше операционной нагрузки сейчас; границы модулей нужно проверять review, а routing/planner позже можно выделить.

**Решение владельца:** получено в запросе начала этапа1; foundation реализован. Независимый mobile backend сейчас не нужен; HTTP DTO и domain ports отделены от Next.js.

## ADR-002 — Локальная геобаза

**Статус:** PostgreSQL/PostGIS утверждены; способ изоляции выбран консультантом в рамках разрешённого этапа1: portable PG17.12/PostGIS3.7 на55433, без системной установки.

**Вопрос:** можно ли подготовить Docker/WSL для изолированной PG/PostGIS, либо нужен native-запуск?

**Рекомендация:** отдельный PostGIS instance на loopback55432, разные dev/test роли/БД, контейнерный digest и поддерживаемая PG17/PostGIS3.x пара. На компьютере есть работающая служба PostgreSQL; её данные/владелец неизвестны, автоматически не использовать. Docker в PATH не найден. Native допустим после проверки версии/расширения/владения и разрешения создать только новую изолированную БД.

**Результат:** своя среда проверена. Существующие5432/55432 не меняются; marker project/cluster/purpose и физический system identifier проверяются до записи/управления. Docker не устанавливался; Compose закреплён digest как альтернатива, здесь не запускался.

## ADR-003 — Пилот и происхождение данных

**Статус:** прежние пилоты заменены ADR-009. Текущие приоритеты: **Firenze, Roma, Milano, Venezia, Napoli**. Исторические казахстанские направления отменены; самостоятельный production-редактор/процесс обновления ещё не назначены.

**Вопрос:** какие два региона, источники и редактор отвечают за первые20 мест?

**Рекомендация:** небольшой вручную проверенный набор из лицензированных источников, metadata лицензии/даты/URL у каждой записи; import dry-run и стабильные source IDs. Массовый scraping и live-зависимость от геокодера не использовать для начального каталога.

**Решение владельца:** география получена, наполнение ещё не разрешено текущим этапом. Источники и ответственный редактор блокируют реальный каталог этапа2, не технический фундамент.

## ADR-005 — Авторизация и сохранение

**Статус:** открыто; **срок:** до этапа5.

**Вопрос:** email+password/reset, OAuth или иной метод; нужен ли перенос гостевого маршрута через вход?

**Рекомендация:** поддерживаемая auth-библиотека с серверной cookie-сессией и проверяемым revoke, без собственной криптографии. Точный продукт выбрать после ADR-007 и review поддержки/security. **Решение владельца:** не получено. **Блокирует:** выбор auth tables/endpoints и выпуск личных данных.

## ADR-006 — Языки и контент

**Статус:** принято владельцем 2026-11-18: поддержка ru/kk/en с первого schema; полный перевод первого технического интерфейса не обязателен.

**Вопрос:** интерфейс первого выпуска ru, ru+kk или ru+kk+en? Кто предоставляет переводы?

**Рекомендация:** модель переводов ru/kk/en с первого schema, первичный интерфейс ru как допущение консультанта; fallback явно маркируется contentLocale. Добавление переводов не должно требовать новых колонок. Не выдавать машинный перевод за редакционно проверенный.

**Результат:** locale types/checks и fallback ru/kk/en реализованы; стартовая техническая страница на русском. Редакционные переводы будущего каталога ещё не собраны.

## Технические решения реализации этапа1

- Geometry(Point4326)+range CHECK вместо канонической geography: это позволяет БД отклонить181° до нормализации; метровые запросы используют geography cast и expression GiST. Проверено на реальной PostGIS.
- SQL runner — node-pg-migrate9 с проектным guard, checksums, advisory locks и запретом автоматических down/destructive statements. Применённые файлы не меняются; исправления отдельными миграциями.
- Исключение GHSA-fc5q-39xc-vjpf действует только для dev=true nodes и до2026-12-18, unknown/prod/expired findings блокируются. Это решение технического review локального инструментария, не объявление отсутствия уязвимостей или разрешение production rollout. ESLint9 EOL отмечен отдельно в DEPENDENCY_REVIEW.
