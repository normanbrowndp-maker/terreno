# Техническое задание

Версия: 0.2, 2026-11-18. Архитектурная основа и этап1 утверждены владельцем. Реализованы только техническая страница, health/readiness, metadata API, модули-порты, схема/миграции и проверки. Функциональные FR-01…16 остаются требованиями будущих этапов. Пилот: Астана/Алматы/Бурабай, данные ru/kk/en. Геймификация запрещена на всех этапах.

## 1. Область и зависимости

Этап 0 завершён. Этапы1–8 выполняются по ROADMAP с проверкой предыдущих ворот; владелец разрешил только этап1. Утверждён Next.js/TypeScript монолит + PostgreSQL/PostGIS; версии и lock уже закреплены в package.json/package-lock.json. pg, node-pg-migrate, Vitest и Playwright установлены; подробности запуска в LOCAL_DEVELOPMENT. Будущая инфраструктура Railway+Neon+AWS SES+Cloudflare задана как ориентир без разрешения подключать/развёртывать.

Рабочие допущения: небольшой коллектив и один web-клиент сейчас; версия API v1 и независимые application ports предусматривают будущий mobile client. ru/kk/en подтверждены владельцем; полные переводы интерфейса на этапе1 не требуются. Источники реального контента и ответственный редактор ещё должны быть определены до этапа2.

## 3. Данные и география

- Страна ISO alpha-2; регионы имеют собственный ID и связь со страной; страна не зашита в таблицы/URL/алгоритмы. Начальный список разрешённых стран содержит только KZ.
- Координаты WGS84, GeoJSON `[longitude, latitude]`, метры/секунды в API, никакого смешения градусов и метров.
- Категории — справочник с переводами, связь многие-ко-многим.
- UUID — стабильный ID; slug не идентификатор владения. Для карточки первого выпуска используется UUID URL; SEO-slug/redirectы можно добавить отдельно.
- Исходные места не удаляются при архивировании; поездка сохраняет ссылку и snapshot названия/точки. При изменении данных пользователь видит устаревание расчёта.
- Даты поездки — date, техническое время — UTC timestamptz, часовой пояс — IANA zone по месту/дню. При расширении не применять часовой пояс Казахстана ко всем странам.
- Деньги при появлении цен: целые minor units + ISO currency, null означает неизвестно; бюджетирование не обещается до отдельной спецификации.

## 5. Безопасность

Весь внешний ввод проверяется на сервере. Параметризованный SQL; allowlist полей сортировки; лимиты длины, числа точек, viewport и request body. Никакого произвольного SQL, HTML и URL для proxy. Описания хранятся обычным текстом первого выпуска; медиа только из контролируемого источника.

БД доступна серверу, не браузеру. Роли runtime и мигратора разделены; runtime без DDL/superuser. Для каждой приватной операции — проверка владельца в SQL/транзакции. UUID сам по себе не заменяет авторизацию. Приватные ответы не попадают в общий cache. Cookie-сессия: HttpOnly, SameSite, Secure при HTTPS; в локальном HTTP отдельная конфигурация. Мутации защищаются проверкой origin/CSRF механизмом выбранной auth-библиотеки. Лимиты login/reset/routes; аудит не хранит содержимое поездок.

Секреты — только локальные env/секрет-хранилище, не Git/next-public/логи. До выпуска аккаунтов нужны политика хранения, удаление/экспорт личных данных и проверка применимых требований к размещению и обработке данных. Юридический вывод в этом ТЗ не делается; облачный регион ещё не выбран.

## 6. Ограничения интеграций

Рендер карты, тайлы, геокодирование, каталог мест и дорожная маршрутизация — разные зависимости. У каждой отдельный adapter/config, лицензия, лимит, timeout и тестовый double. Публичные OSM-сервисы не принимаются за бесплатный production backend. API ключи, платные тарифы, подключение почты и LLM не создаются автоматически.

На этапе 2 поиск идёт по собственной БД, без онлайн-геокодера. На этапе 3 требуется выбранный источник тайлов; на этапе 4 — проверенное покрытие routing по Казахстану; без этого ворота этапа не пройдены. ИИ на этапе 6 опционален: сначала детерминированная проверка выполнимости, затем отдельное решение о LLM и передаваемых данных.

## 7. Общая готовность задачи

Каждая задача TRAVEL имеет цель, небольшой план, зависимости, приёмку, тесты, риски и статус. Перед правкой: проверить рабочее состояние и затрагиваемые зависимости, сформировать diff/план и checkpoint. После: релевантные тесты, регрессия, исправления, документация и свежие свидетельства. Нельзя скрывать failure, отключать проверки, делать destructive migration или изменять production без отдельного разрешения.

Для документации этапа 0 критерии: все обязательные документы; проверенные факты отделены от проектов; ровно первые 10 подробно описанных задач; существующие файлы неизменны; ссылки и контрольная точка проверены. Это не утверждение готовности будущего приложения.
